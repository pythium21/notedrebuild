## 7. API Route Audit

- `/api/share-target` (`src/app/api/share-target/route.ts`): Input validation is present — `rawUrl` is checked for non-empty after trimming (`:21-24`), `NOTED_USER_ID` presence is checked before doing anything (`:15-18`), and the PATCH handler validates both `id` and `title` (`:66-70`). Service role is used correctly per D-009 (client built inline, never exported). Errors are caught via Supabase's own `{ data, error }` return (not try/catch, but equivalent — every Supabase call's `error` is checked) and returned as proper JSON with status codes (400 for bad input, 500 for config/DB errors). [WARNING] This route has no authentication check at all, by design (D-009's whole point is that share-sheet navigations can't reliably carry a session) — but the practical consequence is that anyone who discovers this Railway URL can POST arbitrary URLs and have them written into the app owner's `saves` table indefinitely, with no rate limiting. This is a known, deliberate tradeoff (documented in D-009), not a newly-discovered bug, but it's flagged here as a standing security consideration since the audit brief asked specifically whether this route validates/authenticates correctly — it validates input well but has no auth or rate-limiting layer at all.
- `/api/link-preview` (`src/app/api/link-preview/route.ts`): Validates the `url` field is a non-empty string (`:9-13`), and `fetchPageTitle()` internally guards against non-http(s) protocols and private/loopback hostnames (SSRF defense, `src/lib/linkPreview.ts:17-19,219-220`) with an 8s timeout and 2MB response cap. Failures degrade gracefully — a failed fetch just returns `{ title: null }`, no stack traces or internal error details leak to the caller. [WARNING] Like share-target, this route has zero authentication — it's reachable by anyone on the internet who finds the URL, and its entire job is to make the server fetch an attacker-supplied URL. The private-host guard mitigates SSRF against internal/loopback targets, but it doesn't stop someone from using this as a free, rate-limitless "fetch any public URL through my server" oracle (e.g. for probing which external sites are reachable, or burning the server's outbound bandwidth/CPU on large pages up to the 2MB cap). Low real-world severity for a single-user personal app with no sensitive internal network behind it, but worth a WARNING since it's an unauthenticated endpoint that does outbound network fetches on request.
- Auth check across all API routes: both routes are unprotected, as covered above — no third API route exists.
- CORS/headers: [INFO] Neither route sets any custom headers (CORS, cache-control, CSP, etc.); `next.config.js` is the default empty config with no `headers()` function. This is fine for same-origin same-app calls (which is all that's happening — both routes are only ever called from this app's own client code) and Next's defaults handle `Content-Type: application/json` via `NextResponse.json()`. Not a functional bug, just an absence of any security-header hardening anywhere in the app.

## 8. PWA & Service Worker

- Service worker registration: PASS — `src/components/RegisterServiceWorker.tsx` registers `/sw.js` on mount (guarded by `'serviceWorker' in navigator`), rendered once from `src/app/layout.tsx:32`.
- [WARNING] ✅ FIXED (`9a869d4`) Caching strategy is narrower than documented/intended. `public/sw.js`'s `fetch` handler (`:24-48`) filters every request to `if (!SHELL_ASSETS.includes(url.pathname)) return;` (line 27) **before** branching on `event.request.mode === 'navigate'`. `SHELL_ASSETS` (line 6) is `['/', '/manifest.json', '/icon.svg', '/icon-192.png', '/icon-512.png']` — it does not include `/tasks`, `/projects`, `/saves`, `/pages`, or any other route. The practical effect: the network-first-with-offline-fallback behavior described in the file's own top comment ("lets the installed PWA repaint instantly while the network round-trips") and in MISTAKES.md's stale-shell post-mortem only ever applies to a navigation request for the exact path `/`. A navigation to `/tasks` (or any other route) — the common case for a PWA reopened from the home screen mid-session, since Android/iOS often restore the last-viewed route — never enters the service worker's `respondWith` branch at all; the browser just does its normal fetch, which means no offline fallback and no network-first revalidation for any route except the bare root. This looks like an oversight in the filter's placement rather than an intentional scope limit — the comment and the code's own navigate-mode branch clearly intend to handle "the HTML document" generally, not just `/` specifically. Fixed in `9a869d4`: the navigate branch is now checked first, unfiltered by `SHELL_ASSETS`, and caches every route's successful response under the `/` key so the offline fallback (`caches.match('/')`) works for any route. See MISTAKES.md and BACKLOG.md Active #12 (on-device verification still open).
- Manifest `share_target`: PASS — `public/manifest.json:29-37` points `action` at `/share-target`, matching the actual route (`src/app/share-target/page.tsx`) and BACKLOG.md Active #5's still-open note about the missing `enctype` (confirmed still absent from the manifest — that BACKLOG item is accurately still open, not stale).
- Offline degradation: PASS — no user-facing feature hard-crashes offline. There's no offline write queue (documented, by design, SCHEMA.md/DECISIONS.md), and every data-fetching `useEffect`/handler in the app catches its promise rejection and routes it into a `setError(...)` state rendered as `<p className="auth-error">`, rather than throwing unhandled. Combined with the missing `error.tsx` (Section 4), an unexpected *render-time* exception would still fall through to Next's default error screen, but ordinary offline fetch failures are handled gracefully everywhere checked.

## 9. Security Spot-Check

- Hardcoded API keys/passwords/tokens in source: PASS — none found. All secrets are read via `process.env`.
- Raw SQL via string interpolation: PASS — none found; every DB access goes through the Supabase client's query builder (`grep` for `.rpc(` or template-literal SQL fragments returned nothing).
- `dangerouslySetInnerHTML` or unsanitized user content rendering: PASS — no occurrences anywhere in `src/`.
- [WARNING] Magic-link auth flow (`src/components/AuthGate.tsx`) never inspects the URL for Supabase's own auth-error signal. When a magic link is expired, already used, or otherwise invalid, Supabase redirects back with `error`/`error_description` in the URL hash — `AuthGate` only calls `supabase.auth.getSession()` and subscribes to `onAuthStateChange` (`:17-26`); it never reads `window.location.hash` or `useSearchParams()` for an error param. The practical result: a user who taps an expired/reused magic link just lands back on the plain "enter your email" sign-in screen with no indication anything went wrong — no auth bypass risk, but a real "handles expired/invalid tokens" gap the audit asked about explicitly.
- `SUPABASE_SERVICE_ROLE_KEY` client-side / `NEXT_PUBLIC_`-prefixed leakage: PASS — the only reference to `SUPABASE_SERVICE_ROLE_KEY` in the entire `src/` tree is `src/app/api/share-target/route.ts:10`, inside a route handler, never exported. No `NEXT_PUBLIC_`-prefixed variable anywhere in the codebase carries a service-role or other privileged secret — confirmed by grepping every `NEXT_PUBLIC_` reference (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` — all intentionally public per CLAUDE.md).
