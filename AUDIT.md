## 7. API Route Audit

- `/api/share-target` (`src/app/api/share-target/route.ts`): Input validation is present — `rawUrl` is checked for non-empty after trimming (`:21-24`), `NOTED_USER_ID` presence is checked before doing anything (`:15-18`), and the PATCH handler validates both `id` and `title` (`:66-70`). Errors are caught via Supabase's own `{ data, error }` return (not try/catch, but equivalent — every Supabase call's `error` is checked) and returned as proper JSON with status codes (400 for bad input, 500 for config/DB errors). [WARNING] ✅ ACCEPTED (pre-existing, DECISIONS.md D-009) This route has no authentication check at all, by design (D-009's whole point is that share-sheet navigations can't reliably carry a session) — but the practical consequence is that anyone who discovers this Railway URL can POST arbitrary URLs and have them written into the app owner's `saves` table indefinitely, with no rate limiting. This is a known, deliberate tradeoff (documented in D-009), not a newly-discovered bug, but it's flagged here as a standing security consideration since the audit brief asked specifically whether this route validates/authenticates correctly — it validates input well but has no auth or rate-limiting layer at all. No change: D-009 already owns this decision; D-027 extends the same reasoning to `/api/link-preview`.
- `/api/link-preview` (`src/app/api/link-preview/route.ts`): Validates the `url` field is a non-empty string (`:9-13`), and `fetchPageTitle()` internally guards against non-http(s) protocols and private/loopback hostnames (SSRF defense, `src/lib/linkPreview.ts:17-19,219-220`) with an 8s timeout and 2MB response cap. Failures degrade gracefully — a failed fetch just returns `{ title: null }`, no stack traces or internal error details leak to the caller. [WARNING] ✅ RULED (`2026-08-28`, DECISIONS.md D-027) Like share-target, this route has zero authentication — it's reachable by anyone on the internet who finds the URL, and its entire job is to make the server fetch an attacker-supplied URL. The private-host guard mitigates SSRF against internal/loopback targets, but it doesn't stop someone from using this as a free, rate-limitless "fetch any public URL through my server" oracle. D-027 records the decision to accept this (same class of exposure as D-009's share-target: low-consequence for a single-user personal app, existing SSRF/timeout/size guards deemed sufficient, revisit if abused or if the app stops being single-user). No code change.
- Auth check across all API routes: both routes are unprotected, as covered above — no third API route exists.
- CORS/headers: [INFO] Neither route sets any custom headers (CORS, cache-control, CSP, etc.); `next.config.js` is the default empty config with no `headers()` function. This is fine for same-origin same-app calls (which is all that's happening — both routes are only ever called from this app's own client code) and Next's defaults handle `Content-Type: application/json` via `NextResponse.json()`. Not a functional bug, just an absence of any security-header hardening anywhere in the app.

## 8. PWA & Service Worker

- Service worker registration: PASS — `src/components/RegisterServiceWorker.tsx` registers `/sw.js` on mount (guarded by `'serviceWorker' in navigator`), rendered once from `src/app/layout.tsx:32`.
- [WARNING] ✅ FIXED (`9a869d4`) Caching strategy is narrower than documented/intended. `public/sw.js`'s `fetch` handler (`:24-48`) filters every request to `if (!SHELL_ASSETS.includes(url.pathname)) return;` (line 27) **before** branching on `event.request.mode === 'navigate'`. `SHELL_ASSETS` (line 6) is `['/', '/manifest.json', '/icon.svg', '/icon-192.png', '/icon-512.png']` — it does not include `/tasks`, `/projects`, `/saves`, `/pages`, or any other route. The practical effect: the network-first-with-offline-fallback behavior described in the file's own top comment ("lets the installed PWA repaint instantly while the network round-trips") and in MISTAKES.md's stale-shell post-mortem only ever applies to a navigation request for the exact path `/`. A navigation to `/tasks` (or any other route) — the common case for a PWA reopened from the home screen mid-session, since Android/iOS often restore the last-viewed route — never enters the service worker's `respondWith` branch at all; the browser just does its normal fetch, which means no offline fallback and no network-first revalidation for any route except the bare root. This looks like an oversight in the filter's placement rather than an intentional scope limit — the comment and the code's own navigate-mode branch clearly intend to handle "the HTML document" generally, not just `/` specifically. Fixed in `9a869d4`: the navigate branch is now checked first, unfiltered by `SHELL_ASSETS`, and caches every route's successful response under the `/` key so the offline fallback (`caches.match('/')`) works for any route. See MISTAKES.md and BACKLOG.md Active #12 (on-device verification still open).
- Manifest `share_target`: PASS — `public/manifest.json:29-37` points `action` at `/share-target`, matching the actual route (`src/app/share-target/page.tsx`) and BACKLOG.md Active #5's still-open note about the missing `enctype` (confirmed still absent from the manifest — that BACKLOG item is accurately still open, not stale).
- Offline degradation: PASS — no user-facing feature hard-crashes offline. There's no offline write queue (documented, by design, SCHEMA.md/DECISIONS.md), and every data-fetching `useEffect`/handler in the app catches its promise rejection and routes it into a `setError(...)` state rendered as `<p className="auth-error">`, rather than throwing unhandled. Ordinary offline fetch failures are handled gracefully everywhere checked; a render-time exception is now caught by the route-level `error.tsx` added 2026-08-28 (Section 4) rather than falling through to Next's default screen.
