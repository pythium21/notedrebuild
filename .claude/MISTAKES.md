# MISTAKES.md

Confirmed post-mortems with a known root cause. Undiagnosed bugs live in BACKLOG.md until root-caused.

## Injecting a fresh ReactNode into DrawerContext every render caused an infinite update loop that froze the Notes route

**Root cause** (confirmed via browser harness, 2026-08-08): D-014's `usePageDrawerContent(content)` hook re-fires its effect whenever the `content` node's identity changes, and `PagesShell` passed `renderTree(closeDrawer)` — a fresh JSX node built inline on every render. The effect calls `setDrawerContent`, which re-renders every `useDrawer()` consumer — including `PagesShell` itself, which then builds another fresh node, re-firing the effect: an unbounded update loop. Measured in a standalone browser harness mounting the real `DrawerContext` module: **4,864 renders in one second** with the per-render-node pattern, vs 2 renders with a memoized node. No error is thrown — React yields between commits, so the loop just pegs the main thread indefinitely, which presents as "the page is stuck and nothing responds to taps" (bottom nav included). Only `/pages` injects drawer content, which is why only Notes froze. A second contributing flaw: `DrawerProvider` rebuilt `openDrawer`/`closeDrawer` and the context value object on every render, which would have busted any consumer-side memo depending on `closeDrawer` anyway — both halves had to be fixed together.

**Fix**: `DrawerProvider` now wraps `openDrawer`/`closeDrawer` in `useCallback` and the context value in `useMemo`; `PagesShell` memoizes the injected tree via `useMemo` keyed on the data it renders (`pages`, `pageId`, `loading`, `isCreating`, `closeDrawer`). `usePageDrawerContent`'s doc comment now states the memoization contract explicitly. Verified in the same harness: renders settle at 2, drawer content still injected.

**Lesson**: same as the overflow entry below — this shipped in the drawer-unification batch with build-only verification (`tsc`/`npm run build` can't catch runtime render loops), and the design placed an easy-to-violate identity contract (`[content]` effect dep) on every future caller without stating it. A hook that hands ReactNodes to context must either own memoization itself or loudly document the contract.

## Unbreakable URL titles on Saves expanded the mobile layout viewport, hiding the bottom nav — misdiagnosed twice

**Root cause** (confirmed via headless-mobile reproduction, 2026-08-08): Saves rows whose title is a raw URL (all pre-D-015 rows, and any save whose title fetch fails) render through `.item__name`, which had no `overflow-wrap` handling. Real share URLs (LinkedIn especially) are single unbroken tokens — underscores, `%3A` encodings, long tracking IDs contain no legal line-break points, so the text cannot wrap and overflows the card. On mobile, content that can't fit `device-width` makes the browser **expand the layout viewport itself**: measured in the repro, a 390px viewport grew to 746px. `position: fixed` elements are laid out against the layout viewport, so the bottom nav became 746px wide with its bottom edge at y=1555 on a 390×844 screen — off-screen until you scroll, and showing only its leftmost items ("Today, Tasks") through the 390px visual window. This reproduced every reported symptom exactly, and explains why it was Saves-specific: only Saves renders raw URLs as row titles.

**Why it was misdiagnosed twice**: (1) the autoFocus theory and (2) the `interactiveWidget` theory (entries below) both targeted the viewport/keyboard layer without a reproduction. The layout repro that "cleared" the CSS used a made-up LinkedIn URL containing hyphens — which *are* legal break points — so the text wrapped and the bug hid. The lesson is the repro data has to match the real data's failure-relevant property (here: breakability of the URL string), and a fix shipped without reproducing the symptom is a theory, not a fix.

**Fix**: `overflow-wrap: anywhere` on `.item__name` (lets URL tokens wrap), plus `overflow-x: clip` on `.main` as a hard guarantee that no future child content can widen the page past the viewport. Verified in the same repro: layout viewport back to 390px, nav 390px wide at y=784, all five items visible. `.attached-save__title` already had ellipsis protection — `.item__name` was the gap. The long-URL overflow had been sitting in BACKLOG.md as a P2 *cosmetic* item since before the triage; it was actually the cause of the "unusable" Saves screen.

## Add-task/add-save/add-project inputs auto-popped the mobile keyboard on every page load

**Root cause**: The "add" form inputs in `src/app/tasks/page.tsx`, `src/app/saves/page.tsx`, and `src/app/projects/page.tsx` (the *add* forms specifically — not the inline-edit form in Tasks, which correctly uses `autoFocus` only when a user taps "edit", or the sign-in screen / picker-modal search inputs elsewhere in the app, which fire on an explicit full-screen gate or user-triggered modal open rather than routine navigation) had `autoFocus` set unconditionally. It fired every time the page mounted, not just when the user intended to add something. On mobile this popped the on-screen keyboard immediately on navigation. Originally suspected as the cause of a separate-looking report that Saves' bottom nav was missing (theory: the auto-popped keyboard shrinks the mobile viewport, temporarily pushing the fixed-position bottom nav off-screen) — **superseded**: the actual on-device report described a persistent, scroll-required symptom (only 2 of 5 nav items visible, regardless of keyboard state), which doesn't fit a keyboard-triggered explanation. The confirmed cause is the URL-overflow entry at the top of this file. The autoFocus removal stands on its own merits as a UX fix.

**Fix**: Removed `autoFocus` from all three add-form inputs. Tasks and Saves were fixed 2026-08-08 as part of the original triage batch; Projects' add-form had the identical bug but was missed in that sweep — caught and fixed separately, same day.

## Notes' hamburger drawer used a different breakpoint than the app shell's sidebar, so both could show at once

**Root cause**: `src/components/pages/PagesShell.tsx` built its own hamburger/topbar/drawer for mobile page-tree navigation, switching to its desktop persistent sidebar at `768px`. `NavShell` (`src/components/NavShell.tsx`, wraps every route) switches its own sidebar on at `600px`. Between 600px and 767px, both the app sidebar and Notes' own drawer/topbar could be visible simultaneously — a genuinely different mobile nav pattern on `/pages` than every other route, exactly as reported.

**Fix**: See DECISIONS.md D-014. The hamburger/drawer mechanism moved into `NavShell` itself via a new `DrawerContext`, generalized to every route (empty by default) rather than staying Notes-specific; Notes now injects its page tree into the shared drawer via `usePageDrawerContent()`. The shared drawer switches off at `600px`, matching the sidebar exactly — no more dual-breakpoint gap.

## `interactiveWidget: 'resizes-content'` blamed for the broken bottom nav — attribution superseded, revert kept

**Root cause**: Added to `src/app/layout.tsx`'s `viewport` export to fix the Notes block-editor's slash-command menu rendering behind the on-screen keyboard (fixed-position element pinned to the pre-resize layout viewport). That fix was flagged at the time as strong theory rather than a confirmed root cause, since a component-level test can't simulate a real on-screen keyboard. Reported the same day: the bottom nav (`.bottom-nav`, also `position: fixed`) became effectively unreachable on the installed PWA — needed scrolling to find, and only 2 of 5 items were visible once found. `interactive-widget=resizes-content` is a documented case with exactly this failure mode: it resizes the *layout* viewport (not just the visual one) when the on-screen keyboard interacts, and has known interactions with `position: fixed` elements in standalone/installed-PWA display mode on Android that can leave them mispositioned. No CSS-side bug was found to explain it independently (checked for a `transform`/`filter`/`will-change` on any ancestor of `.bottom-nav`, which would hijack its containing block — none exists; `.mobile-drawer`'s `transform` is a sibling, not an ancestor), so the viewport meta change is the most likely cause given both the timing and the documented mechanism. Not confirmed via direct device testing — this sandbox has no way to test either the original keyboard issue or this regression on a real device.

**Fix**: Removed `interactiveWidget: 'resizes-content'` from `src/app/layout.tsx` (2026-08-08) rather than patching further blind. This reopens the original slash-menu-behind-keyboard problem — see BACKLOG.md for the more scoped follow-up approach (a JS `visualViewport` listener repositioning just the block-menu popup, instead of a global viewport-level setting affecting every fixed-position element app-wide).

**Superseded attribution** (same day): the broken-bottom-nav report this entry blamed on `interactiveWidget` was subsequently reproduced with `interactiveWidget` already removed — the confirmed cause is unbreakable-URL overflow (see the entry at the top of this file). The revert stays anyway: the setting was itself an unverified global change, and the scoped `visualViewport` approach remains the right path for the slash-menu problem.

## Double-submit on Tasks/Projects Add button created duplicate rows

**Root cause**: The `handleAdd` submit handlers in `src/app/tasks/page.tsx` and `src/app/projects/page.tsx` had no loading state guarding the Supabase insert. A user double-clicking Add (e.g. because the request felt slow) fired two `createTask`/`createProject` calls before the first resolved, inserting two rows.

**Fix**: Added an `isAdding` state per form. The submit handler returns early if `isAdding` is already true (guards re-entry even if the UI hasn't re-rendered yet), sets it before the insert, and resets it in a `finally` block so it clears on both success and error. The Add button is `disabled` while `isAdding` and shows "Adding…" as its label.

## Installed PWA briefly showed a stale app shell before real content painted

**Root cause**: `public/sw.js`'s `fetch` handler served `/`, `/manifest.json`, and the icons purely cache-first (`caches.match(event.request).then((cached) => cached || fetch(event.request))`), with no TTL and no revalidation against the network. Once a device's service worker precached `/` on install, it kept serving that exact snapshot — including whichever JS/CSS chunk references were live at install time — on every subsequent launch, indefinitely. Cache invalidation only happened when `sw.js` itself changed (a `CACHE_NAME` bump forces install → activate → purge of old cache keys); a normal app deploy never touches `sw.js`, so returning PWA users stayed pinned to an old shell. This read as a flash of outdated/placeholder content before the real page took over, even though local dev (no service worker involved) never reproduced it and no literal seed/demo data exists anywhere in the codebase — confirmed by checking the production HTML directly, which contains no baked-in task/project content.

**Fix**: Navigation requests (`event.request.mode === 'navigate'`, i.e. the HTML document) now go network-first, with the cache used only as an offline fallback and refreshed from each successful network response. Cache-first is kept only for the static, rarely-changing assets (manifest, icons). `CACHE_NAME` bumped to `my-os-shell-v3` so already-installed clients purge the old frozen entry on next activation.

## Web Share Target wrote to `saves` via the client browser session instead of the service-role pattern

**Root cause**: `/share-target` (`src/app/share-target/page.tsx`) called `createSave()` from `src/lib/saves.ts`, which relies on `supabase.auth.getUser()` finding a live browser session — the same session `AuthGate` gates the rest of the app behind. This was never a documented exception (checked DECISIONS.md — nothing scoped it), and it contradicted D-001's own ruling that any server-side-privileged Supabase access be a route-handler-only `service_role` client. An Android share-sheet navigation isn't guaranteed to carry a persisted, live session in that browsing context, making this an unreliable dependency for a single-user app's most auth-fragile entry point.

**Fix**: See DECISIONS.md D-009. `/share-target` now POSTs to a new route handler (`src/app/api/share-target/route.ts`) that builds a `service_role` client inline and stamps `user_id` from a fixed `NOTED_USER_ID` env var, bypassing session lookup entirely.
